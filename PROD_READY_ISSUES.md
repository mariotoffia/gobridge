## Overview

IDs are stable: closed and withdrawn findings keep their ID and status; new findings continue the numeric series (HIGH-14…, MEDIUM-18…, LOW-20…).
GoBridge is not production-ready for the complete MQTT, clustered high availability (HA), and live-reconfiguration feature set. A constrained single-process or active/standby profile can be operated with trusted publishers, durable compatible stores, stable identity, MQTT Quality of Service (QoS) 1 or 2, idempotent consumers, required telemetry, and tested failover timing. Coordinated cluster rollout remains outside that profile.
The implementation has sound foundations: manual MQTT QoS 1/2 settlement, bounded ingress, durable shared outbox support, lease fencing, restart-monotonic fences for durable pairings, explicit health levels, and a proven compressed owner-death failover path. Since the first audit, chunks 1–4 of `PROD_READY_PLAN.md` closed the identity-trust, URL-alias, binary-correlation, egress-limit, proxy, and accepted-tradeoff findings (`cf86968f`, `84939bf5`, `f0c9685c`, `b781f741`). Confirmed defects still permit loss, ordering violations, stalled delivery, false service-level objectives (SLOs), unbounded lifecycle waits, and permanent mixed cluster generations, and the second pass found seven new HIGH defects: a reconnect-window ack wedge in the MQTT router, SIGTERM cancelling in-flight work before drain in both shipped binaries, cancellation feeding the poison gate, a lease re-seized and held to TTL after session failure, DynamoDB claim ordering and mid-batch claim discard, and a dead runtime retained as current after a failed stop.

## Verified strengths
- MQTT QoS 1/2 acknowledgement waits for runtime settlement. Receive Maximum, bounded queues, count limits, and memory admission provide coherent backpressure for accepted packets. Pending-byte refusal is confined to QoS 0.
- Poison handling chooses bounded, metered loss over infinite persistent-session replay. Direct hold waits for destination acceptance. Durable shared outbox supports persist-before-acknowledgement, fencing, reclaim, and takeover.
- Lease owners fail closed at their local deadline. Managed-subscription changes use durable history and fail-closed reconciliation. Reload builds a replacement runtime instead of mutating the live runtime.
- Readiness has explicit semantic levels. Published modules have no release-blocking `replace` directives. The pinned Paho-version tripwire rejects unsupported software development kit (SDK) drift.

## Verified non-findings
- `AllowUnfenced` does not bypass outbox fencing; it is a validation escape for direct-hold shared consumers. Built-in managers and drainers derive partition and lease identity from the same session ID, so they do not create separate fencing-version spaces.
- `on_expired: dlq` records are not destroyed by bulk expiry. Bulk expiry runs for drop policy; DLQ expiry claims, writes, and completes each record under fencing.
- DLQ redrive injects before delete and rejects a runtime without the safe injection seam. The residual risk is duplication, not delete-first loss.

### BLOCKER-3: Outbox expiry is not fenced
**Status (2026-08-31): Closed.** Landed with Chunk 5 but left unmarked here; re-verified at HEAD `6cfdc8ba` by source trace. `OutboxStore.Expire` now requires the caller's fencing token (`ports/stores_outbox.go:243`) — a coordinated breaking change recorded in `CHANGELOG.md` with the old/new signatures and the three rules an out-of-tree store must implement. Every backend conditions the terminal mutation on it and does so atomically against a concurrent fence raise: memory rejects an invalid token up front and holds `s.mu` across the check and the transitions (`memoryoutbox/store.go:444`), SQLite reads `partitionFenceVersion` and raises the fence inside one transaction (`sqliteoutbox/acl_session.go:429-455`), and DynamoDB pairs each record write with a `ConditionCheck` on the fence row so a takeover landing mid-sweep aborts the remainder (`dynamodboutbox/acl_expire.go:265`). An accepted sweep advances the high-water-mark even when it expires nothing, because on a drop-policy partition whose egress never becomes ready `Expire` is the only fencing call that ever runs. Pinned by the shared conformance suite (`ExpireRejectsZeroToken`, `ExpireRejectsStaleVersion`, `ExpireAdvancesPartitionFence` in `ports/storetest/outbox_fencing.go`), which all three adapters run — including against DynamoDB Local. **Evidence:** `ports/stores.go:192-197` defines `OutboxStore.Expire` without a lease token while `Claim` and `Complete` require one; `runtime/outbox/loop.go:184-215` performs only a local token check. **Trigger/impact:** A caller passes the check, loses its lease, then bulk-expires pending drop-policy records a successor can still deliver. Scope is limited to the drop sweep, but the terminal mutation is unauthorized and destructive. **Required remediation:** Pass the lease token into `Expire`, condition every backend mutation on it, and add stale-owner DynamoDB and SQLite tests.

### HIGH-2: Rollout store calls are unbounded and can disable the deadman
**Status (2026-09-01): Closed.** Every rollout store, coordinator-lease and committed-artifact call now runs through `bridge/rollout_ops.go` under its own budget (`ClusterRolloutConfig.StoreCallTimeout`, 5 s default), by call class (`read`, `vote`, `decide`, `lease`, `artifact`, `propose`) — the applier's observation and votes, the coordinator's Acquire/Renew/Release and its Commit/Abort/Confirm/Revert, the proposer's Propose and join read-back, the artifact write and read-back, and the joiner's two boot reads. A deadline alone was not enough: `context.WithTimeout` expires the CONTEXT, not the CALL, so a context-ignoring client still owned the single drive goroutine. A call that blows its budget is therefore ABANDONED, and while an abandoned call has not returned the barrier starts no new one — so a black-holed store costs exactly one parked goroutine rather than one per tick, and every later tick is instant. The drive now runs `rolloutApplier.tick`, which does the LOCAL safety work first (`rollout_recovery.go`): the confirm-window deadman fires off a cached `provisionalDeadline` instead of behind a store read, so a store outage and a dead coordinator — the same outage from a member's point of view — cannot suppress it. Old observations are marked stale rather than published as if current: `RolloutStatus` carries `ObservationAge`, `Stale` and `LastError`, aged at read time against the last successful read (or, before there has been one, the drive start), and surfaced on `/deephealth` plus `MetricClusterRolloutObservationAge` and `MetricClusterRolloutStoreCalls{operation,outcome}`. Pinned against a context-IGNORING store by `bridge/rollout_ops_test.go`: `TestClusterRolloutOps_NoCallClassStaysBlockedForever` (every call class, plus the single-outstanding rule and its release), `TestClusterRolloutDrive_ShutdownIsNotBlockedByAContextIgnoringStore` (the drive unwinds on its own, given an unbounded stop context), `TestClusterRolloutDrive_StatusGoesStaleWhileTheStoreIsBlackHoled`, and `TestClusterRolloutDeadman_RevertsWhileTheStoreIsBlackHoled` (the member returns to its last confirmed generation while no coordinator decision can be written). **Evidence:** `bridge/rollout_driver.go:117-139` runs applier and coordinator serially; `rollout_applier.go:215-260` and `rollout_loop.go:44-93` pass the long-lived context to remote calls; `rollout_applier_confirm.go:68-76` evaluates the deadman only when that loop advances; `rollout_driver.go:108-111` waits without a bound. **Trigger/impact:** A black-holed or cancellation-ignoring store stops commit, abort, confirm, revert, status freshness, deadman execution, and shutdown. **Required remediation:** Give every call a deadline, run the deadman independently, mark old observations stale, and test a context-ignoring store.

### HIGH-7: Rollout artifact and revert failures are latched as if they succeeded
**Status (2026-09-01): Closed.** Both operations are modelled as retryable state in `bridge/rollout_recovery.go` (`rolloutRepair`: generation, payload, attempts, next-attempt instant), attempted under a bounded exponential backoff based on the poll interval and capped at 30 s. The artifact write is read back through `CommittedConfig` and accepted only when the stored generation is at or above the one written — necessary rather than belt-and-braces, because the port's monotonicity rule makes a write for an older generation a no-op SUCCESS, so "the write returned nil" and "the artifact holds this generation" are genuinely different statements; only then does `artifactGen` advance. ### HIGH-18: The DynamoDB `ClaimIndex` is a global secondary index, so `Claim` can return a younger ordering-key sibling before an older one
**Status (2026-08-18): Closed.** Ordering-keyed partitions are routed to the strongly consistent path: the moment a claim sees ANY ordering key it abandons `ClaimIndex` — having claimed nothing — and re-runs through the `ConsistentRead` base-table scan, which sees every sibling. The LSI alternative was rejected and recorded in ADR 0005 (an LSI can only be created with the table, and caps an item collection at 10 GB per partition key). Pinned by `TestClaim_OrderingKeyedRecords_BypassLaggingIndexForConsistentScan`, which injects index lag through the fake client — the state DynamoDB Local cannot produce — plus `TestClaim_LegacyRecordWithoutOrderingAttribute_StillOrdered` for records written before the `ordering_key` attribute existed; both mutation-checked. ## Message delivery, loss, duplicate, and timeout matrix
There is no exactly-once mode. The strongest supported contract is durable at-least-once delivery with downstream idempotency and possible duplicates.
| Path or event | Settlement behavior | Loss or duplicate outcome | Evidence or signal |
|---|---|---|---|
| MQTT QoS 1/2 `direct_hold`; destination and source acknowledgement succeed | Source held until target acceptance | Delivered once in normal path | Route settlement and manual MQTT acknowledgement |
| Same path; target succeeds but process dies or source acknowledgement fails | Broker redelivers | Duplicate target send possible | Downstream idempotency required |
| Outbound packet exists only in Paho memory at process death | MQTT in-flight state disappears | No protocol exactly-once; source redelivery or durable outbox compensates | Paho egress is volatile |
| QoS 1/2 durable `shared_outbox` with `ack_after: outbox_persist` | Record persists before PUBACK | Crash-surviving at-least-once | Outbox metrics |
| Outbox send succeeds but `Complete` fails/fence changes | Record retries or reclaims | Duplicate send possible | `OutboxDuplicateRisk` |
| Shared outbox uses memory | Acknowledgement can precede process loss of record | Restart loss | Development-only store |
| QoS 0 under queue, shutdown, or emit pressure | No reliable backpressure/redelivery | Best-effort loss | Most queue drops use `MQTTRouterDropped`; emit rejection has no metric |
| Covered QoS 0 byte refusal | Drop without reservation release | Capacity drains until restart | Drop metered; leak is not |

### Reporting boundary
Metrics, events, hooks, and audit publishers are operational signals, not a durable ledger. They can be best-effort or Noop. Conservation needs separate filtered and expired terms. Production requires non-Noop telemetry and alarms; per-message accountability requires a durable terminal-outcome ledger.

## Failover and recovery timing
Conservative owner-death budget:
```text
lease_ttl + 2 * maximum_jittered_acquire_poll
+ (1 + ceil(lease_ttl / minimum_jittered_acquire_poll)) * renew_call_timeout
+ complete MQTT post-takeover activation + startup_allowance
```
MQTT activation is `2 * connect_timeout + 4 * reconcile_timeout + 2 * unmatched_grace`; shipped 30-second values make that term 240 seconds.
| Failure mode or profile | Conservative contract | Verdict |
|---|---:|---|
| Cluster default: 45 s lease, 5 s poll, 3 s call, default activation | About **336.5 s** | No 30–60 s worst-case contract; omission of `failover_slo` logs but does not reject |
| Standalone default: 360 s lease, derived 5 s poll, 5 s call, default activation | About **1,097.5 s** | TTL alone omits observation, calls, polling, and activation |
| Tuned profile: 15 s lease, 2 s poll, 1 s call, 3/2/2 s MQTT | About **49 s** | Can satisfy declared 60 s owner/process-death objective with admission |
| Separate-process test: compressed 5 s lease | **25 s** ceiling | Passed locally; proves mechanics, not defaults |
| Graceful release | No TTL wait | Polling and activation remain |
| `SIGKILL` or node loss | Full observation, polling, activation | Proven on compressed timing |
| Node-local broker outage, default | **Unbounded** | Owner keeps renewing |
| Broker outage with threshold | Threshold + release + polling + activation | Admission omits threshold |
| MQTT settlement recovery | Fixed **5 s** drain; 30 s cooldown can precede another attempt | Unsafe against 30–35 s settlement ceiling |
| Rollout coordinator crash | 30 s lease plus delay/polling | Near/above 60 s; black-holed call is unbounded |
| Session failure on the deferred-connect path (default) | Release, restart, re-seize, release, terminal | One acquire poll (HIGH-17 closed) |
| Derived timings with large `max_renew_fails` | Rejected at preflight | Refused below the 250 ms cadence floor (MEDIUM-24 closed) |
Owner/process/node death can meet 30–60 seconds only with a tuned, declared, admitted, measured profile. Defaults do not. Broker-only default does not fail over; enabled policy lacks trustworthy admission; rollout failure remains unsafe until calls and deadman are independently bounded.

## Runtime and cluster reconfiguration assessment
### Single process
Useful foundations: resolve/validate before build; exclusive identity selects prepare/commit; old runtime remains until candidate preparation; failed candidate attempts old-runtime restore; desired/running version and last error are tracked.
Current limits: every change restarts every session; HTTP and shutdown budgets remain boot-configured; invalid broker-health/backoff can commit before failure; log level mutates before acceptance and ignores unknowns; plan and late-start cleanup gaps remain; apply can outlive HTTP response; settlement recovery can terminalize before bounded send completion.
### Cluster
The protocol has frozen membership epoch, digest agreement, all-member acknowledgement before commit, fenced coordinator election, timeout/Nack abort, optional confirm window, and durable artifact.
It is not production-ready: CDK prerequisites are absent; fingerprint rejects real changes; remote calls can stop progress/deadman; post-commit apply can diverge; artifact/revert failures latch; baseline is not seeded; voter lacks blueprint validation; health omits applied/converged/fresh state. Use controlled whole-cohort replacement with orchestration rollback. Do not call cluster commit cohort-atomic.

## Container and orchestration assessment
Published v0.3.3 digest: `ghcr.io/mariotoffia/gobridge@sha256:e4dbdb80b3d7062b6fe5ac0aa5a921c1e415bbe593979dc35ee0f51714677f7c`. A guarded `latest` also exists; production should pin the digest.

## Production acceptance gate
Do not declare the complete scope production-ready until every BLOCKER/HIGH finding has a composition-boundary regression; hostile properties cannot forge/collapse identity; binary correlation stays stable; URL aliases cannot duplicate owners; MQTT packet/field sizes are enforced; ordering survives claim/store failures; accepted lease/outbox pairs preserve fencing; terminal outbox mutations are fenced; progress-critical calls have deadlines; cooperative close does not restart; declared failover is measured for owner/node/broker/store failure and restart; and a deployed two-member fixture proves propose, vote, commit, apply, convergence, restart, failed apply, revert, and bounded shutdown without permanent mixed state.
The gate also requires black-hole rollout/deadman/SIGTERM tests; explicit rejection of volatile stores from production; no QoS 0 capacity leak; no unrelated terminal failure from a black-holed target; exercised conservation, duplicate, suppression, drop, expiry, DLQ, reconnect, and stranded alarms; authenticated direct TLS, mTLS, proxy TLS, rotation, server-limit, and broker tests; required long-running failover/cgroup gates; builder-valid persistent MQTT examples; a Kubernetes image/probe/flow/reload/drain/restart proof; and documentation tests against endpoint, metric, alarm, config, image, deployment, and failover behavior.

Passing tests and static checks establishes only covered behavior. It does not prove zero bugs, exactly-once delivery, lossless QoS 0, atomic fleet reconfiguration, or a 30–60 second guarantee for every failure mode.
